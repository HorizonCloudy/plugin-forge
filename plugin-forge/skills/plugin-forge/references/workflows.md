# 插件制造专家团 · 工作流手册

> 前置：每次接单先确认目标平台并读对应 profile（见 `SKILL.md` §0）。
> 宪法（T1）优先于本手册；本手册细化流程，不改变宪法。

## Workflow A：从零做一个插件 / 加一个功能（完整七步，不可跳步）

| 阶段 | 执行者 | 产出 |
|---|---|---|
| 1. 分拣 | lead | 任务一句话概括 + 确认目标平台 + 读 profile；确认是"新做"还是"改" |
| 2. 起草方案 | planner（含糊时）→ architect | 方案 ≤500 字：定位 / 入口类型 / 数据 / 依赖 / 验收 / 失败降级 / 风险 |
| 3. **契约审议（门禁）** | **contract** | 准奏 / 封驳（对照 profile 能力面逐条核） |
| 4. 派发 | lead | 按成员拆分，无依赖的并行 |
| 5. 实现 | tdd 先写最小测试 → dev 转绿（ architect / simplifier 并行补位） | 完整代码 + manifest |
| 6. 运行时验证 | sandbox（+ reliability 发布就绪清单） | 隔离环境真实加载记录 |
| 7. 验收汇编 | lead | 三段回奏（见下） |

**不可跳步**：没有 contract 准奏，不许写码。

## Workflow B：修一个跑不起来的插件（单成员直调）

- 已明确是运行时问题（加载失败 / 入口 404 / 权限拒绝）→ lead 直接派 **dev**，必要时
  **sandbox** 复现；回奏注明「单成员直调」。
- 不适用于：要改功能（走 A）、要动架构（走 A）。

## Workflow C：极简重构

simplifier 出删改清单 → architect 附架构图 → reviewer 出修法清单 → lead 汇总。

## Workflow D：沉淀 / 审计一个能力（skill / prompt / 模板）

skill-ops 主导（创建 → 查重 → 审计 → 应用），其余按需。
红线：第三方能力一律「先审计后挂接」；带 hooks / 自动执行脚本的，安装前须取得用户知情同意。

## Workflow E：生态 / 市场缺口分析

1. market-research 抓目标平台插件市场全量 + 官方内置清单 + 核官方文档能力面，
   产出「证据底座 + 缺口地图 + 平台阻塞点」，全部数字带 `[FACT]`（含抓取日期与分母）。
2. 分支：可补强品类 → 转 Workflow A；平台阻塞点 → 整理为"向官方提扩展需求"清单留存。
3. lead 汇编：结论 + 证据分级 + 缺口地图 + 下一步路由。

## Workflow F：运行时验证（"宿主里到底跑不跑"）

1. sandbox 按目标平台 profile 的「沙箱与验证命令」节搭隔离运行时，装入待验插件。
2. 用 profile 声明的**真实存在**的健康 / 列表 / 状态路由判定加载结果；路由面没把握时先
   非破坏性探测（宪法第 10 条），禁止凭想象猜端点（GET 打到只有 POST 的路由会误判成插件故障）。
3. 分支：加载成功但行为不对 → 转 dev 按日志定位；加载失败 → sandbox 归因
   （插件缺陷 / 依赖缺失 / 平台限制 / 沙箱配置错），不许"跑不起来"了事。
4. 边界：沙箱只能证明"能加载、能启动"，**不能**证明"接真模型 / 真数据后效果好"；
   后者属用户环境验收，不得混写。

## Workflow G：文档交付（plugin-forge-docs 执笔）

0. docs 先读 `references/style-anti-slop.md`；引用外部搜集的内容先过 AUDIT（许可证 / 脚本行为 / 提示注入）。
1. 定读者与类型（README / 变更说明 / 长文）。
2. 起草：结论先行；PR/变更说明用三段（Summary+可视化 / Evidence / Merge Danger）。
3. 反 slop：无开场白无收尾、编号步骤、删套话；反 slop 是形式修复，**绝不删事实、数字、条件、范围限定词**。
4. 定稿前过一遍：结构 / 用词 / 事实与范围 / 门禁 四段自检。
5. 交付前核验：英文跑 ste-lint（报告分数）；中文按清单自查。首行末行单独读一遍——读者知道下一步吗。

## Workflow H：宿主破坏性变更影响审计（插件机队体检）

输入：一份宿主侧的破坏性变更公告（RFC issue / changelog / 版本升级）+ 机队范围
（某账号下全部仓库，或指定清单）。产出：逐仓判定（受影响+修改方案 / 不受影响+假阳性说明）。

1. **取公告原文**：宿主自带的自查清单就是扫描规格；没有清单就从"会删除 / 行为会变"
   小节自行推导。不许凭记忆或二手转述扫描。
2. **定机队**：用 API（`gh repo list <account>`）按前缀过滤；不靠本机安装清单或记忆。
3. **扫远端 HEAD**（`gh repo clone --depth 1`）：本机安装副本与仓库是双向差异的
   （本机有仓库里没有的文件，反之亦然），拿任一边当唯一来源都会误判。
4. **命中不等于结论**：每个命中读码归类——真依赖 / 注释 / docstring / vendor /
   测试 fixture / 排除集字符串 / 外部产品同名巧合（如 QQ 平台自己的 openclaw 路径）。
   只有"真依赖"算受影响。
5. **"行为会变"代码扫不出来**：调用方、时机、取消、并发的变化列为人工自查项，
   明说"需逐入口确认"，不许假装已验证。
6. **引用前先核验证据**：公告或任务记录里提到的 PR / 仓库 / 账号，先 API 确认存在再引用
   （实测会碰到 DRYRUN 行里账号根本不存在的假记录）。
7. **回帖礼仪**：宿主说"受影响才回复"——全绿 = 沉默，别发"我也全绿"回执（对维护者是噪音）。
   能发的是 (a) 公告未列出的依赖 (b) 过渡建议；建议必须**可泛化**，
   不许拿"我账号下的插件如何如何"当论据。
8. **环境失败 ≠ 任务失败**：网络不通先分清沙箱拦截 / token 失效 / 站点故障，
   再选路（沙箱放开走 gh CLI；不通再浏览器+剪贴板兜底）。

## 快速问答

「X 是什么」「这插件怎么装」「为什么报 403」——lead 直接答，不开团队流程。

## 封驳重拟（契约审议的回环）

contract 封驳 → planner/architect **只改被驳部分** → 重新送审 → 连续 2 次封驳升级用户裁决
（降范围 / 换方案 / 放弃）。

### 高频封驳原因（提前避开能省一轮）

1. 方案要目标平台没有的 API（对照 profile 能力面"明确不支持"清单）
2. 入口类型用错（如把对话工具入口当运行时入口）
3. 定时 / 周期回调里裸 `raise`
4. 外部输入拼进系统提示词或进 `eval`
5. 没写失败降级

## 验收清单（lead 收货按此勾，全绿才算完成）

- [ ] manifest 语法正确，入口声明与代码一致
- [ ] 入口类型符合 profile 约定（运行时入口 / 工具入口不混用）
- [ ] 纯业务逻辑与宿主 SDK 分层，可离线单测
- [ ] 定时 / 周期回调有异常捕获
- [ ] 网络有超时与失败降级
- [ ] 外部输入不进 `eval`；URL 拼接有编码
- [ ] 数据落盘有清理策略（缓存 / 数据 / 配置分目录）
- [ ] 测试通过（正常路径 + ≥1 边界 + ≥1 错误输入）
- [ ] 安全门禁过（无明文密钥、无注入面、依赖来源可溯）
- [ ] **实际在隔离运行时加载过一次**（或明确标注"未验证"及原因），不是"文件写完就算"

## 三段回奏（最终交付格式）

1. **结论**：插件能装能跑吗 / 功能做成了吗
2. **证据**：改了哪些文件、manifest 关键段、测试与运行时验证输出（带命令与退出码）
3. **需你手动 + 风险**：哪些要在宿主里手动配置、踩到哪些平台限制（引 profile 出处）

## 失败处理

| 情况 | 处理 |
|---|---|
| 加载失败 | sandbox 看日志定位；区分代码问题 / 配置问题 / 平台限制 |
| 契约不符 | 退回重拟方案，不硬改代码将就 |
| 平台做不到 | contract 确认 → 出降级方案 → 用户裁决 |
| 范围蔓延 | 只报告不顺手改；新增需求另开流程 |
