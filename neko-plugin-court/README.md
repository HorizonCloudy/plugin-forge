# NEKO 插件朝议（Edict）

> 把「三省六部制」用在 N.E.K.O 插件开发上 —— **先审契约，再动手写代码**。

## 为什么插件需要「朝议」

做 N.E.K.O 插件最容易翻车的地方，不是写不出代码，而是**方案在 SDK 上根本做不到**：

- 想让猫娘「做个表情回应你」→ SDK 没有 Avatar 表情 / 动作 API
- 想让猫娘「因为你摸她而害羞」→ 没有桌面交互事件
- 想让猫娘「主动生气」→ 没有情绪修改 API

大多数时候，这些是**写了两小时代码才发现**的。三省制的价值就是把「契约审议」放在动手之前 —— 门下省专门负责拦这类方案。

## 结构

```
用户（旨意）
   ↓
太子 ── 分拣 ──→ 中书省 ── 方案 ──→ 门下省 ── 准奏 ──→ 尚书省 ── 派发 ──→ 六部
                   ↑                    │                                    │
                   └──── 封驳退回 ───────┘                                    ↓
用户 ←──────────────── 回奏 ←──────────────── 尚书省验收 ←────────────────────┘
```

## 成员（1 主理人 + 10 成员）

| 角色 | 在插件开发里干什么 |
|---|---|
| **太子**（主理人） | 判断该不该开朝议；回奏时讲清「插件能不能跑」 |
| 中书省 | 出插件方案：入口 / 装饰器 / 数据 / 依赖 / 验收 |
| 门下省 | 按 **SDK 契约**审议，可否决 |
| 尚书省 | 拆任务、并行派发、按产出验收 |
| 工部 | 写 `plugin.toml` / `main.py` / `logic.py` |
| 兵部 | 装插件、查加载路径、排 entry-404 / 启动 failed / model-403 |
| 户部 | 市场数据、能力使用率、下载量 |
| 礼部 | README / i18n / 猫娘话术 |
| 刑部 | 权限、注入、数据落盘、资源滥用审查 |
| 吏部 | skill 盘点、Prompt 调优 |
| 钦天监 | 核 SDK 能力面、确认平台限制 |

## 三条机制

**1. 契约前置** —— 门下省的五维审议里有一维专叫「契约可行性」。方案要的 API 不存在，直接封驳，不许「先写着试试」。

**2. 封驳必须给改法** —— 只否定不给路径算失职。连续两次驳回，升级给你裁决。

**3. 分拣** —— 「这个插件怎么装」这类问答，太子直接答，不走七步流程。

## 四条工作流

| 流程 | 适用 |
|---|---|
| A · 完整朝议 | 做一个插件 / 加一个功能，七步不可跳步 |
| B · 快速问答 | 信息查询、追问 |
| C · 封驳重拟 | 方案被驳回 → 只改被驳部分 → 重新送审 |
| D · 单部直调 | **排障专用**：启动失败直接派兵部 |

## 高频封驳原因（提前避开能省一轮）

1. 方案要 SDK 没有的 API（表情 / 动作 / 情绪 / 桌面事件）
2. 入口用 `@llm_tool` 而不是 `@plugin_entry` + `llm_result_fields`
3. 定时回调里 `raise`
4. 外部文本拼进系统提示词
5. 没写失败降级

## 和 `neko-plugin-ops` 怎么选

| | `neko-plugin-ops` | 本包 |
|---|---|---|
| 结构 | 10 个平级职能专家 | 三省六部分层制衡 |
| 审核 | 主理人自行把关 | 门下省独立否决 |
| 强项 | 覆盖面广、调度灵活 | 流程刚性、契约前置 |
| 适合 | 日常改动、查资料、技能治理 | **从零做一个插件**、方案有 SDK 风险 |
