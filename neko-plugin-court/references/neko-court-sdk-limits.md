# SDK 能力面与平台阻塞点

> 本文件是本团**最重要的一份约束**。它决定了哪些方案从一开始就该被封驳。

## 1. 明确不支持（截至 2026-11，依据官方 SDK 文档核对）

| 想要的能力 | 现状 | 影响 |
|---|---|---|
| 控制 Avatar 表情 / 姿势 / 动作 | **无 API** | 无法做"猫娘做表情回应你" |
| 直接修改猫娘情绪 / 强制某行为 | **无专用 API** | 无法做"让她生气 / 让她撒娇" |
| 桌面交互事件（点击 / 拖拽 / 投喂 / 抚摸） | **无内建事件** | 无法做桌宠式互动 |

→ 任何方案声称要做这三类事，**门下省应直接封驳**，并要求降级或换路径。

## 2. 明确可用

| 能力 | 说明 |
|---|---|
| `OsActivitySnapshot` | 系统活动快照（前台应用、窗口等） |
| `get_os_activity_snapshot()` | 取快照的接口 |
| `bus.frames` | 帧数据通道 |

→ 这些支撑的是**感知型陪伴**：推断用户在干什么，然后**说合适的话**。不是**控制型交互**。

## 3. 由此得出的设计原则

**能做**：感知 → 判断 → 主动说话（推送消息）
**不能做**：感知 → 控制猫娘表现（表情/动作/情绪）

如果你的插件创意核心是"猫娘会对我的动作做出反应"，那它**必然被 SDK 卡住**，只能降级为"猫娘会注意到你在做什么，然后开口说点什么"。

## 4. 勘测方法（钦天监用）

1. 查官方 SDK 文档与仓库（`Project-N-E-K-O/N.E.K.O`）
2. 查不到 → 标 `[未核验]`，**不臆断"应该可以"**
3. 给替代方案，哪怕只是"降级为感知"

## 5. 结论三档

- `[确认支持]`：文档有明确章节
- `[确认不支持]`：文档明确无此能力
- `[未核验]`：文档没写 / 取不到 → 不做承诺

## 6. 待核验清单（随官方更新而变化）

- SDK 是否新增了 Avatar 控制相关接口
- `bus.frames` 的字段是否扩展
- 是否有新的桌面事件通道
- 插件权限模型是否有调整

> 每次会话开始刷新能力底座时，若 SDK 版本或文档有变，须同步更新本文件并标注核验日期。
