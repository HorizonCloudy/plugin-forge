# 来源与定位说明

## 1. 两条来源

| 来源 | 用途 |
|---|---|
| `https://github.com/cft0808/edict` | 提供**制度模型**：三省六部的分权制衡、封驳机制、分拣规则、防注入红线 |
| `Project-N-E-K-O/N.E.K.O` 官方 SDK 文档与仓库、`market.project-neko.cn` | 提供**业务事实**：插件契约、SDK 能力面、市场数据 |

**制度模型参考上游，业务内容来自 N.E.K.O 官方资料与本机实测。** 未复制 edict 的源码（那是 Python/React 运行时系统，不是专家包）。

## 2. 与本机另一专家团的关系

本机已有 `neko-plugin-ops`（NEKO 插件设计与自动运维专家团），两者**业务重叠但组织形态不同**：

| | `neko-plugin-ops` | `neko-plugin-court`（本包） |
|---|---|---|
| 结构 | 1 主理人 + 10 个**平级职能专家** | 三省六部**分层制衡**结构 |
| 审核 | 由主理人自行把关 / 按需调 reviewer | **门下省独立审议，可否决** |
| 强项 | 覆盖面广、调度灵活、技能面完整（13 份 references） | 流程刚性、契约前置、适合"从零做一个插件" |
| 弱项 | 审核不独立，"自己批自己" | 流程重，小改动显冗余 |

**怎么选**：从零做一个插件、或方案有明显 SDK 风险 → 用本包；日常改动、查资料、技能治理 → 用 `neko-plugin-ops`。

## 4. 未继承 / 未做的部分

- edict 的看板 CLI（`kanban_update.py`）、FastAPI、React dashboard、飞书接入、心跳监控 —— **均不在本包内**，本包是"角色 + 规则"，运行态由宿主提供
- edict 的 `zaochao`（早朝定时晨报）—— 本包以用户发起为唯一入口，未纳入
- edict 上游的工部/兵部职责冲突 —— 本包按"工部=工程实现、兵部=安装运行时"处理，符合 N.E.K.O 语境（安装排错是独立技能）
